# 多网络数据面：源地址 NAT 与已知限制

## 背景：单 tun 多地址的源地址缺陷

PacketTunnelProvider 只有一个 packetFlow（单一 utun），多网络时把各网络地址聚合配到同一接口。iOS 内核发包时**源地址总选接口主地址（第一个配置的地址）**，与目的网段无关；`NEIPv4Route` 只有目的和网关、无源地址绑定，路由层无法干预。

表现为：双网络同开时，发往后加入网络网段的包源地址是另一网络的地址，对端回包无法路由回来——只有一个网络可用（文件顺序里第一个），关掉它另一个立即恢复。

## 修复：数据面轻量 NAT（PlanetPortTunnel/NAT44.swift）

- **出站**：路由选中网络后，源 IP 不属于该网络且属于本机另一网络地址时，改写为该网络地址（优先选与目的网段匹配的地址），按 RFC 1624 增量修正 IP 头与 TCP/UDP 校验和；TCP/UDP 按 `nwid + 四元组` 登记流表（不换端口，纯地址改写）
- **入站**：命中流表的回包把目的地址回写为手机原始源——内核 socket 本地地址是那个错误的原始源，不回写则 TCP 握手匹配不上
- **流表**：512 条上限，LRU；TCP 6 小时 / UDP 60 秒空闲老化，双向任一包刷新活跃时间
- 单网络场景源不可能错，零改动直通

诊断（App 诊断页）：`NAT出/NAT入`（ctx 行）、`NAT流表`（首行）、`源不符`（检测计数留证）。

## 已知限制

| # | 限制 | 原因 | 影响 |
|---|------|------|------|
| 1 | **IP 分片不进流表** | 非首片无端口无法匹配四元组 | 分片回包不做目的回写，内核重组时目的地址不一致会丢；ZT 内部 MTU（2800）内基本不分片，仅应用发超 MTU 大 UDP 包时触及。出站方向非首片仍会改写源（只修 IP 头校验和，不碰载荷），入站是残留断点 |
| 2 | **ICMP 差错报文送不回原始 socket** | 差错报文内嵌的原包头源已是改写后地址 | NAT 化的 TCP 流收不到 PMTUD/不可达提示；不做 NAT 该流本来也不通，非回归 |
| 3 | **广播/组播不做源改写** | 组播扇出到所有网络，无单一"所选网络"语义 | 双网时组播包源仍是主地址（mDNS/DHCP 跨 ZT 发现本就不依赖它，维持现状） |
| 4 | **超长空闲后对端先发包会断** | 流表按空闲老化（TCP 6h）；条目失效后对端先发的包无回写被内核丢弃 | TCP 重传或手机侧任一出站包即自愈重新登记；真实保活间隔均为分钟级，6h 窗口覆盖所有常规协议 |
| 5 | **IPv6 不做 NAT** | 当前场景 v6 未启用（aggV6=0、可关） | 若未来双网都下发 v6 地址且内核选源有同样问题，需按本文思路扩展 NDP/流表 |

## 相关诊断字段速查（ctx 行）

- `源不符=N(IP)`：出站源不属于本网络的检测计数（NAT 生效时应与 NAT出 同步增长）
- `ARP答=N@时刻`：最近一次 ARP 应答时间（双网故障时用于锁定时间相关性）
- `待决=[IP×数量] 最老=Ns`：ARP 未解析的下一跳明细
- `核心拒=N(code=…)`：`processVirtualNetworkFrame` 非 OK 返回码
- `收问=a/b`：入站 ARP 请求总数 / 其中命中本网地址数
